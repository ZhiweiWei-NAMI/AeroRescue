# 平台功能闭环验收：用户最新口径（覆盖旧场景通过率口径）

用户明确要求：必须区分 agent 能力不足与平台设置问题。目标是逻辑上各功能闭环，平台提供可正确调用的功能/API；调度策略造成的未通过可忽略。不要继续优化自主策略或用场景总目标通过率判定平台功能。

在既有工作树和已有证据上继续，不重启已有服务，不引入多代理评审。先建立功能/API矩阵，再只针对缺失证据做最小验证或修复。

分类必须有证据：
A agent策略/调度：未选正确执行者、未发出动作、错误顺序、优先级争用、未计划路径；不计入平台API失败，不为此优化自主策略。
B 场景/平台配置缺口：缺接收站、库存/容量不足、合法能力未配置、装备绑定缺失。与API实现缺陷分开；不得说成agent不够聪明，也不得无证据说API不可用。
C 平台API/状态流转缺陷：合法调用且前置条件满足，仍拒绝、无正确效果、状态不一致、确认或事件不完整。修复并复验。
D 证据不足/未覆盖：明确待验证，不能混入失败或通过。
合法前置条件检查本身不是过度防御；错误或互相矛盾的条件才是平台问题。禁止通过直接写成功标志掩盖错误。

交付矩阵按当前任务范围覆盖感知/区域评估、接触确认、解困、急救、真实物资领取、装载、水上回收、运输、接收确认、抑火、隔离、通路恢复，以及运行入口/事件/回放。核对原计划与动作注册表确定范围，不扩展新产品功能。每行写 API/动作、合法前置条件、输入、实际状态变化、事件证据、是否闭环、缺陷类别。优先复用SC09/SC13/SC07等已有真实链证据，避免全场景全量重跑。

对于配置缺口，可创建明确隔离的最小API测试fixture来提供所需站点/库存/容量等，以验证API本身；必须保留原场景配置不变，并同时报告原场景缺口及测试前置条件。fixture通过不等于原场景通过。现有规则air定位覆盖只能证明后续API链，不能证明原地面移动API；地面移动需合法可达条件下独立核验。

立即更新 execution-status.md 标明新口径，随后完成 platform-api-closure.md 与 machine-readable matrix。已通过的功能只引用证据；未覆盖的最小补测；真实平台缺陷修复。必要相关回归一次即可，避免另起长时间生成/相机推理/策略优化。保留真实接收确认、库存/载荷一致性等核心效果断言。汇报平台功能闭环、配置缺口、可忽略策略失败，三者不可混为一个通过率。
